By 2026-09-24 we had clicked "Continue with GitHub" on the first real deployment of the App, in production, and nothing happened. No spinner, no redirect, no request in the network panel. The only sign of life was a line of text: "The operation failed."

Locally it had worked. Three commits across five days dealt with the first real hostname, and each fixed something our local runs were never going to show us.

## The button that sent nothing

The App and the API live on different hostnames in production. The API sets its anti-forgery cookie, `XSRF-TOKEN`, as a host-only `SameSite=Lax` cookie on its own hostname. A page on another hostname cannot read that cookie. The App's sign-in function needs to read it and echo it back in a header, so it threw before the generated client ever made a request. That is why there was nothing in the network panel: the failure happened one line before the request would have been sent.

The session cookie has the same shape of problem, only more so. It carries the `__Host-` prefix, which by definition cannot be shared across hostnames.

Our local runs did not put the App and the API on separate hostnames, so that code path passed there. It was tested thoroughly, in the wrong world.

The fix, committed on 2026-09-24 at 23:34 Pacific, was not to loosen the cookie. We left both cookies' attributes alone. Instead, the Cloudflare Pages worker for the App, which infrastructure code renders, now reverse-proxies the API's versioned surface onto the App's own origin, so the cookie is same-origin and readable. The App's expected API origin became its own origin in production and staging, and the generated client's base path became same-origin. The API's origin policy already trusted the App's origin, so nothing changed on that side. The one exception is the schema documentation origin, which stays on the API's hostname because it carries no credentials.

A proxy changes where the request goes. It does not change what either cookie permits.

## The binding that only knew local

Three days earlier, on 2026-09-21 at 23:34, we had fixed a different blocker that the same first deployment would have hit. The App validates a small file, served at runtime, that tells it which origins to talk to. It compares that file against an expected binding. We had compiled the expected binding for local development into every build, unconditionally. A real staging or production deployment would have validated every served file against the local tuple, failed with `ENVIRONMENT_MISMATCH`, and sat permanently degraded. The commit message calls it "the App's production blocker."

A local run could not have caught it, because the local binding always matched itself.

The fix selects the expected binding by a build-time environment value, from three committed fixtures for local, staging and production, generated by the infrastructure code's renderer so the two cannot drift on origin values. A missing or unrecognised value fails closed. It does not default to local. A bare build, which is what our own gate runs, deliberately leaves the value unset, so the resulting artefact refuses to pick a binding at runtime. That is uncomfortable when you first meet it and correct when you think about it.

## The policy that was written from the source

On 2026-09-25 at 08:51 we widened the App's content security policy. The first pass had been written from what the repository's own source loads. Then someone opened the deployed origin in a real browser.

The commit says it plainly: a live browser check "found two more real violations, one of them blank-screening the App entirely". The validator for the runtime-origins file is compiled at run time by a schema library, and compiling a validation function needs `'unsafe-eval'`. Static analysis of our source could not have told us, because the code that needed it is generated by a library we import. The second violation was Cloudflare's own zone-level Web Analytics beacon, loaded from a separate Cloudflare host next to the challenge-platform loader we had already allowed. That script is not in our repository at all; it comes from a zone-level setting, so no reading of our own source could have listed it.

A policy derived from your source describes your source. The browser enforces it against what the server actually sends.

## What you can use

Each of these three failed the same way: the check ran in an environment that could not produce the failure.

1. **Write an auth test that crosses hostnames.** If the real deployment puts the front end and the API on different hostnames, a test where they share one has not tested cookies. Run the pair on two hostnames, even two local ones, before you trust it.
2. **Make the build environment explicit and fail closed.** A default that silently picks local is a default that ships local to production.
3. **Test your content security policy by loading the deployed page in a real browser and reading the console,** not by reading your own bundle. Do it on the first deploy, not the tenth.
4. **Treat "the button does nothing" as a cookie, header or policy problem until proven otherwise.** When there is no request at all, the failure is upstream of the network.
5. **Prefer moving the request to loosening the credential.** The proxy fix changed neither cookie's attributes, and the commit says so in as many words, because the next person to read it will go looking for exactly that.

How long the deployment was unusable, and whether any user reached it in that state, is not stated in our records.
